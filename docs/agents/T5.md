### How the old slice and the new code fit
`BeatmapDB(BeatmapDBStore*)` / `setStore` (batch 37/38) still works: a non-owning store, only delete/update, the new methods are no-ops (like Java with `connection == null`).
`init(factory, paths)` / `init(unique_ptr<SqlConnection>)` makes the object **own** the connection, create a `SqlBeatmapDBStore` on it and use that as `store_`. `closeConnection()` releases all of it (an externally set store is left alone).

## Deviations from the Java
1. `BeatmapParser.getDBString` (string interning) **not ported**: memory optimisation, no behaviour.
2. SQL `NULL` in a Java String field reads as `""`; `md5Hash`/`bg`/`video` are written NULL when `""`; on load a NULL `bg`/`video` leaves the field unchanged (Java: `if (bg != null)`). NULL `audioFile` -> SQLException "audioFile is NULL" (Java: NPE inside the try that wraps to SQLException).
3. `insert(batch)` on failure: **rollback + restore auto-commit** and the cache size is unchanged (Java left the connection in manual-commit mode with pending rows).
4. `init` failure after connecting closes the connection again (Java kept a half-initialised static connection).
5. Java's `System.out.println("OsuDB SQLExec ...")` is `Log::debug`. `e.printStackTrace()` after "Failed to move old database" is a line on stderr.
6. Instance, not static; `delete(dir,file)` / `delete(dir)` are the existing `deleteMap` / `deleteGroup`. `File.lastModified()` is a seam (`setLastModifiedProvider`, default mtime in ms).
7. `DBController::createConnection` error text: Java's `Could not connect to database: '<path>'.` followed by `\nCaused by: <cause>` in `what()`.
8. Every public `BeatmapDB` method takes one recursive mutex (Java only synchronised `load(Beatmap)` and `setStars`): see below.

### Java quirks kept (found while testing, same in the Java)
- An **empty non-null** `breaks` list is stored as `''` and then cannot be loaded (`"".split(",")` -> `[""]` -> `Integer.parseInt("")` throws; the load reports "Failed to load Beatmap from database." and skips the array fields). The Java parser leaves `breaks` null when there are none (real db: 107 NULL, 0 empty).
- `cacheSize` comes from `info.size` and is never recounted (real db: `size = 233`, 227 rows). A pre-`info` database starts at 0.
- An unreadable stored version (`garbage`, NULL) is treated as 0: all updates run again, the 7 ALTERs fail (warnings) and the UPDATEs reset `favorite`, `playCount`, `lastPlayed`, `localOffset`, `videoOffset`, `stars`.
- On an `info` row without `size`, `cacheSize` = 0; on a SQL error reading it, it stays -1 (Java's initial value).

## Thread-safety rules
- `SqliteConnection` opens with `SQLITE_OPEN_FULLMUTEX` (serialized) and a 3000 ms busy timeout. **One connection may be used from many threads. One statement / result set object must be used by one thread at a time** (they hold per-statement state; the Java shares its prepared statements the same way, under `synchronized`). A prepared statement's result sets share the compiled statement: only one open result set per prepared statement, and re-executing invalidates the previous one (same as JDBC).
- `executeUpdate` row counts are exact across threads (a per-connection mutex around "step + read changes").
- `BeatmapDB`: every public method locks one recursive mutex, so the shared `insertStmt` / `selectStmt` / store statements, `cacheSize` and the connection are never used concurrently. Consequence: a long `load(batch)` table scan blocks inserts and updates until it finishes. The file is `EXCLUSIVE`-locked, so a second connection to the same file (another process or object) gets `SQLITE_BUSY` after 3 s: use one `BeatmapDB` per file.
- Closing a connection with statements still alive is safe (`sqlite3_close_v2`; they are finalised when destroyed). Do not use a connection from a thread while another closes it.
- `Download::reportError` and `Log` are called from the calling thread (under the BeatmapDB mutex): the handlers must not call back into the same `BeatmapDB` from another thread and wait for it.
