## Deliberate differences from Java
1. **Fades are ticked, not threaded.** Java `Music.fade/pitchFade` start a thread each (sleep 10 ms). Here `Music::updateFades()` runs them from the game thread; `MusicController::updateMuffle(delta)` calls it every frame, so the integrator needs no extra hook. A new fade replaces a running one; `dispose()` cancels fades. Pitch fade keeps Java's "stop at the first step past the duration without applying it".
2. **Java bug kept: `Music.setVolume(float)` is empty**, and `Music.fade()` calls it. So `MusicController::fadeOut()` does not ramp the volume; it only pauses after `duration`. Same for `MusicController::resume()` (`setVolume(1.0f)` does nothing). If you want an audible fade, change the two `setVolume(` calls in `Music::updateFades` to `setMusicVolume(` (src/audio/MusicController.cpp). I did not do it because the Java is the reference.
3. **Java quirk kept:** `MusicController::play()` sets `lastBeatmap` even when the load failed (or the extension is not ogg/mp3). Retrying the same file is then a no-op until `reset()` or another file.
4. **Dropped:** the `trackLoader` thread (commented out in Java, `isTrackLoading()` is always false), `Utils.gc()` thread, `destroyOpenAL` internals (commented out; dropping the last reference disposes the backend track), `GameContainer.setMusic`, `SoundStore.soundWorks()` (always true), `PulseAudioFixerListener` (desktop Java Sound only), and the `LineEvent` argument of `LineListener` (the game never reads it): clip end callbacks are `std::function<void()>`.
5. `SoundController::playTrack`: Java's `new URL(url)` failure becomes "no `scheme:` prefix" -> bar notification `Failed to load clip '<url>'.` and `false`.
6. `loadBeatmapSamples`: files visited in name order (Java: directory order); lower-casing is ASCII only.
7. Clock: audio code uses `audioMillis()` (steady clock) instead of `System.currentTimeMillis()`; the "no timing info" beat progress is therefore a 60 bpm pulse with an arbitrary phase (it was wall-clock-phased in Java).
8. `MusicController` keeps a `const Beatmap*` to the beatmap given to `play()` (Java keeps the reference): call `reset()` before that `Beatmap` is destroyed. `getBeatmap()` returns the pointer (nullptr = none); `getBeatProgress()` returns `float` (never null in Java either), `getMeasureProgress()` returns `std::optional<float>`, timing points are returned by value.

## Contract changes (for T2, BASS)
Already sent with the three headers; the full list again:
- `AbsMusic` has `onRequestSync` (Java `AbsMusicCompleteListener.requestSync`) + protected `fireMusicEnded()` / `fireRequestSync()`, and non-pure `volFade` / `pitchFade` (Java defaults). The game never calls them (the `Music` wrapper does its own fades); you can ignore them.
- `IAudioBackend::createStreamClip(const std::string& url)`; registry takes `std::shared_ptr<IAudioBackend>`.
- Lead-in (negative positions) is handled by `Music` in core: it calls `AbsMusic::setPosition(0)` + `pause()` and starts the track later itself. The backend never sees a negative position.
- `Music::dispose()` calls `AbsMusic::dispose()` at most once and clears `onComplete`/`onRequestSync` right before. `BassMusic::dispose()` must remove its BASS syncs (`BASS_ChannelRemoveSync`) and must not fire callbacks after it returns, or the callback would run into a destroyed `Music`.
- `Clip` calls `ClipImplementation::destroy()` in its destructor (Java left that to the GC), so `destroy()` must be idempotent.
- Callbacks (`onComplete`, `onRequestSync`, a clip's `onEnd`) must be marshalled to the game thread by the backend, as written in AGENT_TASKS.md.
- For T8: `trackActive` = `MusicController::trackExists()`, `currentAudioFilename` = `MusicController::getBeatmap()->audioFilename` (when non-null), `resetTrack` = `MusicController::reset()` (stops, releases the backend track, clears the beatmap pointer).

## Tests
`tests/test_audio_t1.cpp` (all on a fake clock, so it is exact and instant; ~190 checks):
- registry fallback to silent; silent backend: position advances, pause freezes, seek, negative seek clamps to 0, pitch changes keep the position and scale the speed, stop/loop/dispose, default no-op FFT/levels/low-pass;
- `Music`: smoothed position, lead-in (virtual clock, backend held at 0 and started at the exact position, pause/resume/pitch inside the lead-in, skip out of the lead-in), completion listener, FFT/levels only while playing, single dispose, load failure -> `runtime_error`;
- fades (pitch step values, end without applying, volume fade pauses, dispose cancels);
- `MusicController`: missing track, unsupported extension, preview start, volume = music * master * start scale, same track / new preview time, offsets (global + beatmap-local, `setTrackPosition`), pause/resume/pitch/dim, track end + loop, FFT, load failure through the error seam, reset releases the track, theme song, beat/measure progress and timing point advance (inherited points), muffle sweep (log-frequency midpoint = sqrt(20000*300), monotonic, no repeated calls, volume-adjust hold, restore, new track while muffled), `fadeOut` / `pitchFadeOut` through `updateMuffle`;
- `SoundController`: init (skin dir first, wav/mp3/ogg order, resources, missing-file errors), volumes, mute, `playSoundChecked`, `HitSound.getClip()` null until a sample set is chosen, lazer hit sounds (layered rule, own volume, 5% minimum, sample sets, additions), slider tick, beatmap samples (name rule, referenced names, `.wav` preferred, custom index suffix, object sample file), loops and sliding sounds (stop all, mute, gameplay-sounds-off, auto stop on destruction), intro sounds, `playTrack`/`stopTrack`, sound disabled, re-init destroys old clips;
- `MultiClip`/`Clip` (id 0 ignored, destroy in destructor, stream clip, silent backend no-ops).

Not golden-tested against the real Java: there is no JVM in this sandbox and the code has no float/locale output to compare (positions are float arithmetic ported statement by statement; the muffle math is checked analytically).
