## Java quirks kept (so behaviour matches; the Java may want a fix later)
- `dispose()` destroys only the single images; the frame arrays (`defaultImages`) are left alone and `isSkinned` is not reset.

## For the Game state port
`states/Game.java` lines ~894-896 hold the legacy-name rule that is NOT part of `GameImage`:
```
Image arrow = GameImage.ARROW_WARNING.getImage();
if (arrow == null) arrow = GameImage.WARNINGARROW.getImage();
```
Port it as `auto arrow = gameimage::getImage(GameImage::ARROW_WARNING); if (!arrow) arrow = gameimage::getImage(GameImage::WARNINGARROW);` (the same helper is in test 6). `ARROW_WARNING` is optional, so it is silent when missing; `WARNINGARROW` is a normal entry and logs an error if it is missing too.

## Seams (set once at start-up)
- `gameimage::setHost(GameImageHost)`: `getMobileUIScale`, `loadHDImages`, `isBeatmapSkinIgnored`, `resourceExists(bareName)`, `fontLargeLineHeight`, `fontDefaultLineHeight`, `isListed` (SkinCache). Empty members use the defaults written in the header.
- `gameimage::setSkinInfo(shared_ptr<const SkinInfo>)`: directory, animation framerate, font prefixes, menu glow.
- `gameimage::init(width, height)`: screen size; UI scale = height / 768.
- `resourceExists` gets the bare name (`"hitcircle.png"`); the loader then opens the asset `"res/hitcircle.png"`. It is never checked with `std::filesystem`.

## Deviations from the Java
1. **API shape:** an enum class has no methods, so `GameImage.CURSOR.getImage()` is `gameimage::getImage(GameImage::CURSOR)`. The brief's `setSkinImage(...)` does not exist in the Java; the Java name `setBeatmapSkinImage(File dir)` is kept.
2. **Default skin:** the brief says "default = no skin". With no skin, the Java loads nothing at all, so the default here is a `SkinInfo` with no folder (res/ images load). `setSkinInfo(nullptr)` gives the Java "no skin" state.
3. **Images** are `shared_ptr<Image>` (the C++ `Image` cannot be copied; an `Animation` shares the frames with the GameImage, as in the Java). An absent image or array is a null pointer or an empty vector.
4. **Blank images:** a file that cannot be decoded gives a blank image in both versions (no failure). The Java catch blocks for `SlickException` are kept (log + continue), but the C++ `Image` constructors do not throw for bad files.
5. **Errors the Java would crash on, guarded here:** `init()` not called (Java: ArithmeticException) throws `std::logic_error`; `FitButtonBgHeight` with `MENU_BUTTON_BG` missing (Java: NPE) logs an error and leaves the image unscaled; `getAnimation` with no image returns an empty `Animation` and logs; a skin framerate <= 0 other than -1 is treated like -1; `setImage(img, index)` with an index out of range is ignored (negative included).
6. **Case-insensitive file names** use ASCII lower-casing (the Java uses Unicode folding).
7. **`ErrorHandler.error`** is `Log::error` (no dialog, no report).
8. **The `ARROW_WARNING` vs `WARNINGARROW` rule is not in `GameImage`.** The Java only declares `ARROW_WARNING` as optional (may be absent everywhere); the rule "use the legacy name only if the new one is absent" is in the caller, `states/Game.java` lines ~894-896 (`getImage()` of `ARROW_WARNING`, falling back to `WARNINGARROW`). Test 6 covers the `GameImage` part (optional entries are silent and remembered as absent). The fallback will come with the port of `Game`.

## How to re-run the generator
From the repository root (needs only Python 3):
```
python3 -I docs/agents/T11_tools/gen_gameimage_table.py <path to GameImage.java> \
        app/src/main/cpp/core/src/GameImageTable.cpp app/src/main/cpp/core/include/opsu/GameImage.h
```
`--dump` prints every distinct `process_sub` body. If the script stops with "unknown override body", add the new body to `PROC_KINDS` in the script and implement the new `ProcKind` in `GameImage.cpp`. Running it twice gives identical files.
